Plugin Architecture — Two Loading Models

Model A — Classpath Plugin (default)

A Spring @Component in the main application classpath. Annotate with @CmsPluginMeta. Auto-discovered by PluginRegistry.discoverAndActivateClasspathPlugins() at startup. Can use @EventListener natively. Cannot be uninstalled via UI — requires a redeploy.

Model B — External JAR Plugin

A self-contained JAR file uploaded via POST /api/admin/plugins/upload. Loaded via URLClassLoader. Must contain a plugin.json at the JAR root. Instantiated reflectively. Installed, activated, deactivated, and uninstalled at runtime — no server restart needed.

Developer Usage — Writing a Plugin

Classpath Plugin (simplest)

@Component  // Makes it a Spring bean — auto-discovered
@CmsPluginMeta(
    id          = "my-custom-plugin",
    name        = "My Custom Plugin",
    version     = "1.0.0",
    author      = "Your Name",
    description = "Does something amazing.",
    permissions = { "CONTENT_READ", "EMAIL_SEND" },
    autoActivate = true
)
public class MyPlugin implements CmsPlugin {

    @Override
    public void onActivate(ApplicationContext ctx) {
        // Register anything dynamic here
    }

    @EventListener  // Hooks into CMS Event Bus
    public void onFormSubmitted(FormSubmittedEvent event) {
        // React to every form submission
    }
}

External JAR Plugin — plugin.json

{
  "id": "my-external-plugin",
  "name": "My External Plugin",
  "version": "1.2.0",
  "author": "Third Party Dev",
  "description": "Adds DOI resolution to research papers.",
  "entryClass": "com.example.DoiResolverPlugin",
  "permissions": ["CONTENT_READ", "EMAIL_SEND"],
  "dbMigrations": [],
  "autoActivate": true
}

Plugin Lifecycle

StatusTransitionCmsPlugin method called
—First install (upload or classpath boot)install(ctx)
INSTALLED → ACTIVEAdmin clicks ActivateonActivate(ctx)
ACTIVE → INACTIVEAdmin clicks DeactivateonDeactivate()
INACTIVE → ACTIVEAdmin clicks Activate againonActivate(ctx)
ANY → UNINSTALLEDAdmin clicks Uninstall (JAR only)onUninstall() then JAR deleted
Security note: JAR plugin loading uses URLClassLoader which shares the parent classloader. Production deployments should add a security manager policy or use OSGi for true isolation. The permissions declared in @CmsPluginMeta are recorded in the DB but runtime enforcement is a Phase 8 hardening task.
