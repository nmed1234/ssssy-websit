SSSSY CMS — Enterprise SDK & Plugin Architecture

Deep-thinking blueprint for evolving the current Spring Boot + Next.js system into a WordPress/Drupal/DNN-grade extensible platform — with developer SDK, plugin system, dynamic form engine, and universal API gateway

Part 1 — How Standard CMS Platforms Actually Work

Before designing the architecture, understand what makes Drupal, WordPress, DNN, and Joomla powerful. Every one of them is built around four core pillars:

1. Hook / Event System
Every core action fires an event (hook). Plugins listen and modify behaviour without touching core code. WordPress add_filter, Drupal hook_node_save, DNN IPortalModule.
2. Dynamic Content Types
Admin defines fields at runtime. No code deployment needed. Drupal "Content Type" with CCK fields, WordPress Custom Post Types + ACF, Joomla "Articles" with custom attributes.
3. Dynamic Form Engine
Field definitions stored in DB. Frontend renders forms from JSON schema. Submission validated against schema. Stored in a generic "submissions" table — no migration per form.
4. Plugin / Module System
Self-contained packages (PHP files, JAR, DLL) that register routes, forms, menus, and DB tables on install. Platform provides a registry — plugin just implements an interface.

Key insight: Your CMS already has 297 Java files and 60+ frontend pages. The missing layer is extensibility infrastructure — the hooks, the form engine, the plugin registry, and the developer SDK. Everything else is already built. The plan below adds exactly those layers without rewriting the core.

Part 3 — Target Architecture (5 Layers)

Layer 5 — Developer SDK & Plugin Runtime

TypeScript @ssssy/cms-sdk npm package + Java cms-plugin-api JAR. Developer writes a plugin, calls SDK hooks, deploys.

Layer 4 — Dynamic Form & Content Type Engine

CMS stores field definitions as JSON schema in DB. API endpoint auto-generated. Frontend form rendered from schema. Submissions stored in generic table.

Layer 3 — CMS Event Bus (Hook System)

Spring ApplicationEventPublisher wrapped in CmsEventBus. Every save, publish, delete fires typed event. Plugins subscribe via @CmsEventListener annotation.

Layer 2 — API Gateway with Auto-Generated Endpoints

Dynamic controller resolves /api/v2/content-types/{typeName} at runtime using the field registry. No new Java controller needed per content type.

Layer 1 — Existing Core (unchanged)

Current 297 Java source files, Spring Boot, PostgreSQL, MinIO, Redis, 60+ Next.js pages remain as-is. New layers sit on top.

Part 4 — The 7 Major Features to Build

Feature 1 — Dynamic Content Type Engine (like Drupal's Content Types)

Admin creates a "Research Paper" type with fields: title, abstract, author, PDF, DOI. The CMS stores this as a JSON schema. Immediately:

  • A CRUD REST endpoint GET/POST/PUT/DELETE /api/v2/dt/research-paper is auto-generated
  • An admin form to create/edit entries is auto-rendered from the schema
  • A public page /research-papers/{slug} is auto-rendered using the SDK renderer
  • The workflow engine attaches the default or custom workflow
  • Sitemap and SEO metadata automatically include the new type

DB Schema (new tables)

-- stores the type definition
content_type_definitions (
  id UUID PK,
  name VARCHAR(100) UNIQUE,      -- "research-paper"
  label_en VARCHAR(255),
  label_ar VARCHAR(255),
  description TEXT,
  icon VARCHAR(100),
  workflow_id UUID FK workflows,
  allow_comments BOOLEAN,
  allow_member_submit BOOLEAN,   -- KEY: members can submit
  requires_approval BOOLEAN,
  is_active BOOLEAN,
  sort_order INT,
  created_at TIMESTAMPTZ
);

-- stores every field of every type
content_type_fields (
  id UUID PK,
  content_type_id UUID FK,
  field_name VARCHAR(100),       -- "abstract"
  field_label_en VARCHAR(255),
  field_label_ar VARCHAR(255),
  field_type VARCHAR(50),        -- text|richtext|number|date|media|relation|select|checkbox
  is_required BOOLEAN,
  is_searchable BOOLEAN,
  is_listed BOOLEAN,             -- show in list view?
  options JSONB,                 -- for select: [{value,label}]
  validation_rules JSONB,        -- {min,max,pattern,message}
  sort_order INT
);

-- stores actual data for all dynamic content types
dynamic_content_entries (
  id UUID PK,
  content_type_name VARCHAR(100),
  slug VARCHAR(550) UNIQUE,
  status VARCHAR(30),
  author_id UUID FK users,
  workflow_state VARCHAR(50),
  field_data JSONB,              -- {"abstract":"...","doi":"..."}
  published_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ,
  updated_at TIMESTAMPTZ
);

Feature 2 — Dynamic Form Engine (like Drupal Webform / Gravity Forms)

Admin builds any form visually (drag-drop fields). Form JSON saved to DB. Frontend renders it. On submit, validation happens server-side against schema. Data stored in a universal submissions table. Admin sees all submissions. Can trigger workflow or email notification on submit.

Key fields

forms (id, title_en, title_ar, slug, schema JSONB, success_message, redirect_url,
        email_notification_to, workflow_trigger, is_active)

form_submissions (id, form_id FK, user_id FK nullable,
                  data JSONB,        -- the submitted values
                  ip_address, user_agent, status, created_at)

Form schema example (JSON stored in DB)

Frontend rendering: One universal <DynamicForm slug="paper-submission" /> component reads the schema and renders the correct inputs. Zero code change to add a new form — admin does it all in UI.

Feature 3 — CMS Event Bus (Hook System)

This is the most critical extensibility feature. Every meaningful action in the CMS fires a typed event. Plugins and internal services listen. No coupling between emitter and listeners.

Java SPI pattern

// Plugin developer writes this:
@Component
public class MyResearchNotifier implements CmsEventListener<ContentPublishedEvent> {
    @Override
    public void onEvent(ContentPublishedEvent event) {
        if ("research-paper".equals(event.getContentType())) {
            // send email to all subscribers
        }
    }
}
// Registered automatically via Spring @Component — no core code change

Feature 4 — Plugin / Module System (like WordPress Plugins)

Developers package their code as a self-contained unit. The CMS provides a plugin registry.

Backend Plugin (JAR)
  • Implements CmsPlugin interface
  • Declares metadata via @CmsPluginMeta annotation
  • Can register: REST endpoints, event listeners, scheduled jobs, DB migrations
  • Dropped into /plugins/ folder → hot-loaded via Spring child context or @Import
  • DB: plugins table tracks install state, version, config
Frontend Plugin (JS bundle)
  • A Next.js dynamic import bundle or an npm package
  • Registers page-builder blocks via CmsSDK.registerBlock()
  • Registers admin menu items via CmsSDK.registerAdminRoute()
  • Registers public page renderers via CmsSDK.registerContentRenderer()
  • Listed in admin → Plugins → Frontend Extensions

Plugin manifest (plugin.json)

{
  "id": "sssy-research-portal",
  "name": "Research Portal Plugin",
  "version": "1.0.0",
  "author": "SSSSY Dev Team",
  "entryClass": "org.ssssy.plugins.research.ResearchPlugin",
  "frontendBundle": "research-portal-ui.js",
  "dbMigrations": ["V100__research_portal.sql"],
  "permissions": ["CONTENT_READ", "CONTENT_WRITE", "EMAIL_SEND"],
  "configSchema": {
    "doi_resolver_url": { "type": "string", "default": "https://doi.org/" }
  }
}

Feature 5 — Member Article Submission with Workflow (the full loop)

This is the most requested feature and it uses ALL the above systems together. Here is the exact flow:

  1. Member logs in → sees "Submit Article" in their dashboard
  2. Fills dynamic form — title, body (rich editor), category, tags, cover image, optional co-authors
  3. Clicks Submit → POST /api/v2/member/articles → status = PENDING_REVIEW
  4. Event fired: ContentCreatedEvent → notifies all EDITORs via real-time notification + email
  5. Editor opens approval queue → reviews full content with diff view
  6. Editor actions:
    • Approve → status = APPROVED → event → PUBLISHER notified
    • Request Revision → status = REVISION_REQUESTED → member gets email with comments
    • Reject → status = REJECTED → member notified with reason
  7. Publisher sets publish date (immediate or scheduled) → status = PUBLISHED
  8. ContentPublishedEvent fires → SEO metadata auto-created, sitemap updated, newsletter optional
  9. Member sees their article live on the public site with their author profile

The workflow is fully configurable — admin can define a simpler 2-step (member submits → admin publishes directly) or a 4-step editorial workflow using the workflow UI that already exists in the CMS.

Feature 6 — TypeScript SDK Package (@ssssy/cms-sdk)

Developers install this npm package and can call any CMS capability from a button, component, or page without hand-crafting fetch calls.

SDK surface API

import { CmsClient, useContent, useForms, useWorkflow } from '@ssssy/cms-sdk';

// Initialize once
const cms = new CmsClient({ baseUrl: process.env.NEXT_PUBLIC_API_URL });

// React hooks provided by SDK
const { data, loading } = useContent('research-paper', { status: 'PUBLISHED' });
const { submit, status }  = useForms('paper-submission');

// Button wired to API with zero boilerplate
<CmsFormButton
  formSlug="paper-submission"
  label="Submit Your Paper"
  onSuccess={(submission) => router.push('/thank-you')}
/>

// Workflow action from a button
<CmsWorkflowButton
  contentId={article.id}
  action="APPROVE"
  label="Approve Article"
  requiredRole="EDITOR"
/>

// Register a custom page-builder block
CmsSDK.registerBlock({
  type: 'research-citation',
  label: 'Research Citation',
  icon: 'BookOpen',
  schema: { doi: { type: 'text', label: 'DOI' } },
  render: ({ doi }) => <CitationBlock doi={doi} />
});

Feature 7 — Admin Plugin Manager (like WordPress plugin screen)

A dedicated admin panel at /admin/plugins:

  • Lists all installed plugins with status (active/inactive), version, permissions used
  • Upload a plugin ZIP → server unpacks → validates manifest → runs DB migrations → activates
  • Activate / Deactivate / Uninstall with one click
  • Plugin settings page — rendered from plugin's configSchema
  • Plugin marketplace (future) — browse community plugins from a registry URL
  • Security: permissions sandbox — plugin only gets what it declares

Part 7 — Critical Design Decisions & Tradeoffs

JSONB vs. EAV vs. Separate Tables for Dynamic Content
Decision: JSONB
PostgreSQL JSONB with GIN index gives full-text + operator queries. Drupal uses EAV (slow). WordPress uses postmeta (slow). JSONB is the modern standard (Contentful, Sanity, Strapi all use it).
Plugin Isolation Strategy
Decision: Spring child ApplicationContext
Each plugin runs in its own child context. Beans from plugin can access parent services. Parent cannot see plugin beans by default. Prevents plugin conflicts. Safer than OSGi for Spring Boot.
API Versioning
Decision: /api/v2/ for new engine
Keep /api/v1/ hardcoded controllers unchanged (no breaking change). Dynamic content types live under /api/v2/dt/{typeName}. SDK targets v2. Gradual migration of v1 types to v2 in Phase 8.
Frontend Plugin Loading
Decision: Dynamic import + CmsSDK registry
Next.js dynamic() + a CmsSDK global registry. Plugin JS bundle calls CmsSDK.registerBlock() on load. No webpack rebuild needed per plugin — loaded at browser runtime from CDN/MinIO URL.

Do NOT rewrite the core now. The 297 Java files and 60+ pages work. Extensibility layers sit ON TOP. Existing APIs remain stable. Phase 8 migration is optional and low-risk because it's additive (new DB tables, new routes, data migration only).

Summary — The 3 Sentences That Capture Everything

Your CMS already has the content — it needs the plumbing. Add an event bus (the hook system), a form engine (the dynamic submission system), a content type engine (runtime field definitions), and a plugin SPI (the developer SDK). This turns a custom-coded website into a platform — one where developers add features by writing plugins, not by modifying core code.
