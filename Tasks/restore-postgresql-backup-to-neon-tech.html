Restore Backup to Neon.tech (Railway DB)

Replace your Neon PostgreSQL database with db/fullBakupfinal.sql — 0.33 MB pg_dump from PostgreSQL 17.5

⚠ This will DELETE all current data in Neon and replace it with your backup. The backup owner is ssssy. Neon's default owner is neondb_owner. The steps below handle the owner mismatch automatically.

Option A — Using psql (Recommended, fastest)

PREREQ PostgreSQL client tools installed locally (psql, pg_restore). Since you created the dump with pg_dump 17.5 you already have them.

1Drop & recreate the public schema — clears existing data 
psql "postgresql://neondb_owner:npg_CSEwZ1Ag9Gyh@ep-jolly-tooth-asms1hcn.c-4.eu-central-1.aws.neon.tech/neondb?sslmode=require" ^
  -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"

On Linux/Mac remove the ^ line continuation — use \ instead, or write it on one line.

2Restore the backup — replacing owner ssssy → neondb_owner

The dump contains OWNER TO ssssy but Neon uses neondb_owner. Fix on the fly with sed (Linux/Mac) or PowerShell (Windows):

Windows PowerShell

$sql = Get-Content "db\fullBakupfinal.sql" -Raw
$sql = $sql -replace 'OWNER TO ssssy', 'OWNER TO neondb_owner'
$sql = $sql -replace 'Owner: ssssy', 'Owner: neondb_owner'
$sql | psql "postgresql://neondb_owner:npg_CSEwZ1Ag9Gyh@ep-jolly-tooth-asms1hcn.c-4.eu-central-1.aws.neon.tech/neondb?sslmode=require"

Linux / Mac (bash)

sed 's/OWNER TO ssssy/OWNER TO neondb_owner/g; s/Owner: ssssy/Owner: neondb_owner/g' \
  db/fullBakupfinal.sql | \
  psql "postgresql://neondb_owner:npg_CSEwZ1Ag9Gyh@ep-jolly-tooth-asms1hcn.c-4.eu-central-1.aws.neon.tech/neondb?sslmode=require"

Errors like "role ssssy does not exist" or "ERROR: must be owner of extension pgcrypto" are harmless — Neon pre-installs pgcrypto. Continue past them.

3Verify the restore 
psql "postgresql://neondb_owner:npg_CSEwZ1Ag9Gyh@ep-jolly-tooth-asms1hcn.c-4.eu-central-1.aws.neon.tech/neondb?sslmode=require" ^
  -c "\dt" -c "SELECT count(*) FROM users;"

You should see your tables listed and a row count > 0.

Option B — Neon Web Console (no CLI needed)

1Open Neon Console

Go to console.neon.tech → select your project → SQL Editor tab.

2Drop existing schema

Paste and run:

DROP SCHEMA public CASCADE;
CREATE SCHEMA public;
3Prepare the SQL file for Neon

Since the SQL Editor doesn't accept file uploads, first generate a cleaned copy locally:

PowerShell

$sql = Get-Content "db\fullBakupfinal.sql" -Raw
$sql = $sql -replace 'OWNER TO ssssy', 'OWNER TO neondb_owner'
$sql = $sql -replace 'Owner: ssssy', 'Owner: neondb_owner'
# Remove CREATE EXTENSION lines (Neon pre-installs them)
$sql = $sql -replace 'CREATE EXTENSION IF NOT EXISTS pgcrypto.*\n', ''
Set-Content "db\fullBakupfinal_neon.sql" $sql

Linux / Mac

sed 's/OWNER TO ssssy/OWNER TO neondb_owner/g; s/Owner: ssssy/Owner: neondb_owner/g' \
  db/fullBakupfinal.sql > db/fullBakupfinal_neon.sql
4Paste into SQL Editor

Open db/fullBakupfinal_neon.sql in a text editor, select all (Ctrl+A), copy (Ctrl+C), paste into the Neon SQL Editor, click Run.

The file is only ~0.33 MB so it fits in the editor without issues.

Option C — Railway DB Plugin (if you switch from Neon)

Only if you want to move the database from Neon to Railway's own PostgreSQL plugin. Skip this if staying on Neon.
  1. Railway Dashboard → your project → + New → Database → PostgreSQL
  2. After it provisions, click the plugin → Connect tab → copy the DATABASE_URL
  3. Run Option A's psql commands but replace the connection string with the Railway one
  4. Update the Railway service Variables: set SPRING_DATASOURCE_URL / DB_URL to the Railway DB URL

After Restore — Reset Flyway

Important: Your backup already contains all the tables in their final state. Flyway will try to run migrations again on next startup and fail because the tables already exist.
You must tell Flyway the migrations are already applied.
Option 1 — Mark all migrations as applied (safest) 
psql "postgresql://neondb_owner:npg_CSEwZ1Ag9Gyh@ep-jolly-tooth-asms1hcn.c-4.eu-central-1.aws.neon.tech/neondb?sslmode=require" ^
  -c "SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;"

If the flyway_schema_history table is already in your backup (it should be — pg_dump includes all tables), Flyway will see it and skip already-applied versions. No action needed if the table exists in your dump.

Option 2 — If Flyway table is missing from backup

Add spring.flyway.baseline-on-migrate=true to Railway env vars temporarily, then remove after first successful start.

# Railway env var to add:
SPRING_FLYWAY_BASELINE_ON_MIGRATE=true
